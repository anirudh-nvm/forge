# Adaptation Principles

These rules are unbreakable. No code in the adaptive layer may violate them.

## Rule 1: No Silent Changes

Forge never changes the user's schedule without explicit approval.

Every adaptation must be presented as a proposal. The user must actively choose to accept it.

## Rule 2: Evidence Over Anecdote

Learned preferences always come from completed experiments, never from a single observation.

One good morning does not create a morning preference. A pattern across multiple experiments does.

## Rule 3: Fixed Means Fixed

Fixed commitments are never moved. College, work, recurring obligations — these are structural. Adaptation only touches flexible tasks.

## Rule 4: Explain Every Adaptation

Every adaptation must be explainable in plain language.

Example: "Morning DSA was suggested because the 'Morning Study' experiment improved completion from 58% to 86%."

If Forge cannot explain why, it should not suggest it.

## Rule 5: Failure Reduces Confidence, Not Capabilities

A failed experiment removes confidence in a preference instead of permanently banning it.

Contexts change. What failed in winter might work in summer. The door stays open, but trust is earned back.

## Rule 6: Small Experiments First

When uncertain, suggest the smallest possible experiment.

Don't propose a full schedule overhaul. Propose changing one task for one week.

## Rule 7: Respect the User's Rhythm

Forge adapts to the user, not the other way around.

If the user prefers evenings even when mornings show better metrics, that preference wins. The goal is improvement within the user's life, not optimization against it.

## Rule 8: Transparent Confidence

Always show confidence levels.

High confidence = multiple experiments, consistent results.
Low confidence = few experiments, mixed results.

The user should see the evidence, not just the recommendation.
